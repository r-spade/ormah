This spec replaces the auto-linker's full-table scan with an internal change-sequence cursor. The problem is quadratic cost repeated every 24 h; the approach is a durable seq counter plus a watermark, serving both backfill and incremental modes through one mechanism. The hard parts — transient vs. poison LLM failures, durable allocation, and bounded recall — are isolated in correctness.

The problem ↑

run_auto_linker (src/ormah/background/auto_linker.py) scans every node each run and, per node, re-encodes its text, runs a brute-force vec_store.search (itself O(n)), and calls the LLM per surviving candidate. Total cost is O(n²) compute + O(candidates) LLM calls, repeated every auto_link_interval_minutes (default 1440 = 24 h). _find_link_candidates — the maintenance-protocol preview, reached via get_maintenance_batches → maintenance_manager — has the same shape, and additionally sorts with ORDER BY RANDOM().

auto_link_checked already skips already-evaluated pairs, but only after the expensive encode + search — so the scan cost stays unbounded in n regardless. On the real store (8,355 nodes) most of each run is spent re-encoding and re-searching nodes that yield nothing: 4,776 nodes (57%) have never produced an evaluated pair.

The approach ↑

An internal change-sequence cursor. A single mechanism serves both backfill (drain the historical backlog) and incremental (only new or changed nodes), differing only in the watermark's initial value.

Council change · crit. #2 An earlier draft used a (updated, id) watermark over the domain timestamp. But created / updated come from the markdown frontmatter (builder.py:128), so historical imports, restores, and index rebuilds insert rows with timestamps behind the watermark — permanently invisible to the scan. Replaced with an internal monotonic change-sequence, bumped wherever node content is (re)written.

Council v2 · crit. #1 An earlier draft used MAX(seq)+1, which is not monotonic across INSERT OR REPLACE — the deleted row's seq gets recomputed and can collide. A durable counter (meta.node_seq_next) fixes this: it only ever increases, regardless of which rows currently exist.

full_rebuild() resets the watermark to 0 (builder.py:23 — the single point all rebuild paths funnel through: startup FTS migration, rebuild_index / POST /rebuild, restore). Defensive: the durable counter already keeps rebuilt nodes above the watermark, but the reset also covers a wiped-meta rebuild. See the full_rebuild() branch in the flow below. (Council v2.)

Write-to-watermark flow ↑

A content write allocates a seq from the durable counter; the cursor then drains everything above the watermark, one node at a time, advancing the watermark only past fully-resolved nodes. The three LLM branches — see correctness — decide whether a node is resolved.

The two consumers ↑

Both consumers share the same incremental select. The difference is whether they advance the watermark — only run_auto_linker does.

ConsumerSelectWatermarkCost
run_auto_linker seq > :watermark ORDER BY seq ASC LIMIT :max_nodes_per_run advances to the seq of the last fully-resolved node O(batch · n)
_find_link_candidates same incremental select; replaces ORDER BY RANDOM() reads only — side-effect-free preview, never advances O(batch · n)

The inner match logic is unchanged: encode → vec_store.search → cross-space penalty → threshold → auto_link_checked/existing-edge skip → _llm_classify_link → _apply_edge. Only the outer driver — what rows it iterates — changed.

The replaced select, in full 
SELECT id, content, title, type, space, seq FROM nodes
WHERE seq > :watermark ORDER BY seq ASC LIMIT :max_nodes_per_run

This replaces SELECT ... FROM nodes (all rows). The watermark advances to the seq of the last fully-resolved node — see correctness for what "fully-resolved" means across the three LLM branches.

Correctness ↑

Five properties hold. The three load-bearing ones — the LLM None/error split, the durable counter, and bounded recall — are called out below.

New & changed nodes both re-enter Δ · crit. #2 fixed Every content write bumps seq past the watermark via the single builder site, so reindex / import / restore are covered by construction — independent of markdown timestamps. A node update also deletes the node's auto_link_checked rows (memory_engine.py :806 / :850 / :1201 / :1206), so its pairs are re-evaluated.
Transient LLM failure retries; poison node never deadlocks · crit. #1 v1 + crit. #2 v2 _llm_classify_link distinguishes two failure cases — see the flow diagram branches. LLM unavailable (raw is None) → returns None → the node is left unresolved and the watermark does not pass it (next run retries). This is the transient case (Ollama down) and does not deadlock: when the LLM is down, every node is unresolved, so the whole run simply waits — no single node blocks others. Invalid / unexpected output (malformed JSON or missing relationship) → returns {"relationship": "error"} → _apply_edge records result='error' in auto_link_checked (no edge) and the node is treated as resolved, so the watermark advances. A content-specific "poison" pair therefore never blocks later nodes. (An error pair is re-tried only if the node's content changes — which bumps seq and clears its auto_link_checked rows.)
Bounded recall, stated honestly · importante #3 vec_store.search(limit=6) returns only the top-6 neighbours, and top-k membership is not symmetric — a pair where neither node is in the other's top-6 is never evaluated. This is a pre-existing limit of the full scan too; the cursor additionally removes the re-scan "second chance". Accepted as bounded recall (not lossless); revisiting strategies are out of scope for this perf fix.
PropertyWhy it holds
Partial run / crash / max_edges hit mid-node The watermark only advances to the last fully-resolved node; reprocessing is idempotent (checked pairs skipped, no duplicate edges).
No ties seq is unique and monotonic, so the cursor is a single integer — no composite comparison needed.
